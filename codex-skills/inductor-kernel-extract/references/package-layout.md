# 命名与精简交付

需要多文件、多用例或对照模式的组织细节时读取。本参考提炼“原 kernel + 直接输入恢复 + 短比较脚本 + 真实日志”的交付方式；文件名和数量是按问题选择的，不是接口标准。

## 文件角色与命名

| 角色 | 可选命名示例 | 选择依据 |
|---|---|---|
| kernel 与输入准备 | `repro_softmax_fwd.py`、`repro_attention_dq.py`、`<原kernel名>_repro.py` | 能看出实际算子/阶段；对方按生成名称定位时保留原名 |
| 比较或运行入口 | `compare_softmax.py`、`compare_failing_kernel.py`、`run_compile_repro.py` | 精度问题体现比较，编译/运行时问题不伪装成数值测试 |
| 解释器结果 | `interpreter_result.log`、`cpu_interpreter.log` | 仅在确实执行解释器后提供，不把CPU eager叫解释器 |
| 设备/编译结果 | `npu_result.log`、`compile_result.log`、`runtime_failure.log` | 体现实际验证阶段；必要对照可分文件或分段 |
| 独立数据/IR | `inputs.pt`、`reference.pt`、`failing_kernel.mlir` | 仅在内嵌/直接构造不合适或IR本身是入口时添加 |

文件命名优先级：用户指定 > 接收方现有约定 > 实际算子/阶段/用例身份。选简短、可辨识、便于命令行引用的名称，多例用子目录或必要后缀避免冲突。不要沿用无关的 Issue 编号、kernel 序号、算子名称或 `_failing` 等已经不适合的标签。

改变外部文件名不等于修改 kernel 内部标识。通常保留原函数、绑定名和编译元数据中的 kernel 名，以便和日志/IR对应；确有必要改符号时同步引用并验证，不靠全局字符串替换。程序按显式相对路径或参数加载目标，不扫描目录自动挑一个同名 kernel。

## 按任务裁剪

- **精度 + 可用解释器**：可采用 kernel（含data）、比较脚本、解释器日志、NPU日志这四个角色；解释器不是强制项。
- **只有设备数值复现**：kernel、必要比较脚本和设备日志即可；小脚本可合并比较入口。
- **编译/运行时失败**：提供 kernel 或固定 IR、实际启动入口和失败日志，不编造 golden 或增加无意义的比较脚本。
- **多用例**：通常每例一个可独立转交的小目录；确有共享需求可复用比较器/数据，但单独转交时应包含这些依赖。

内嵌数据与独立数据都可选。内嵌时保留原序列化精度及必要布局/别名，编码段放文件末尾，使 kernel 和调用仍易读；大数据或共享数据用包内相对文件。不要为了适配命名增加 manifest、来源字典、通用恢复框架或环境哈希校验。

## 简单入口的职责

kernel 文件负责原代码、必需 helper 和直接可读的输入准备；比较/运行脚本负责选择实际设备、启动、同步、比较和非零失败退出。`prepare_inputs(device)` 之类的小函数可以使用，但名称、返回值和参数数量按实际 kernel 确定，不强制迁移成通用 API。是否支持直接执行 kernel 文件，取决于是否能让交接更简单；不要为了双入口制造循环导入。

只有确需解释器/设备切换或编译开关对照时才添加相应参数。验证该版本环境变量/选项的实际行为，帮助文本、默认值与日志一致。默认入口应能复现所交接的问题，不默认开启使失败消失的对照选项；对照仅说明影响，不把关闭开关称作已完成生产修复。

文件头通常足以交代必要环境、运行命令、参考来源与边界，不另外凑 README。最终回复给包链接、实际入口和简短结果；只有接收方确实需要额外说明时才单独成文。

## 不从成功案例复制的内容

复用结构和可读性，不复制历史路径、卡号、环境版本、shape、grid、dtype、误差阈值、输出编号、golden 公式、编译开关或预期结果。沿用原算法与数据语义，每个用例单独验证；文件名和包装可以调整，失败机制及比较标准不能为了“更简洁”改变。
